Mein Voice-Agent war blind — und der Fix passte in ein einziges Attribut

Ada hatte alle Unterlagen bekommen. Im Gespräch tat sie, als hätte sie nie eine gesehen. Die Spurensuche — und warum der Fehler nirgends „im Code“ saß.

Lesezeit ~4 Min · Stack: Next.js · FastAPI · Supabase · ElevenLabs Conversational AI

TL;DR

Symptom: Hochgeladene Dokumente (GuV, KPIs, Hotelprofil) erreichten den Voice-Agent „Ada“ nicht.

Wurzel: Der 24.000-Zeichen-Briefing wurde als ElevenLabs Dynamic Variable übergeben — und die werden ab ein paar Tausend Zeichen still verworfen.

Fix: Den vollen Per-Call-Prompt über override-prompt übergeben statt über eine Variable. Eine Zeile.

01Das Symptom

Der Ablauf im Studio ist einfach: Ein Hotel lädt im Onboarding seine Unterlagen hoch — Gewinn- und Verlustrechnung, Monats-KPIs, Personalstruktur, Prozessdoku. Danach führt es ein Sprach-Interview mit Ada, der KI-Stimme, die daraus eine Analyse baut.

Ich lade also acht Dokumente hoch. Das Onboarding meldet brav: „✓ verarbeitet“. Ich starte das Gespräch. Und Ada fragt mich Dinge, die in den Unterlagen schwarz auf weiß stehen. Sie kennt meinen Umsatz nicht. Sie kennt meine Auslastung nicht. Sie ist — blind.

02Der erste Reflex (und warum er falsch war)

Der erste Gedanke ist immer derselbe: „Das Backend ist kaputt.“ Naheliegend, fast immer falsch. Statt zu raten, habe ich die Daten an jeder Grenze der Kette geprüft — vom Upload bis zur Stimme. Genau da, an einer dieser Grenzen, verstecken sich diese Fehler.

03Die Spurensuche

Vier Stationen waren grün. Eine war rot. Und die rote war keine, die man im Quellcode sieht:

  • Backend erreichbarapi.myflowmotion.cloud → HTTP 200
  • Dokumente sauber geparstDB-Check: parsed_text vorhanden, 800–4.100 Zeichen pro Datei
  • Backend baut den Briefing — MIT den Dokument-Datenvoice_session.system_prompt = 23.931 Zeichen, enthält GuV / ADR / Auslastung
  • Frontend übergibt den Briefing ans Sprach-Widgetdynamic_variables.briefing_context wird gesetzt
  • ElevenLabs-Gespräch: der Briefing kam NIE anangekommen: first_name (4), company_name (10), data_recap (2.379) — briefing_context (~20.000): fehlt

Der entscheidende Beweis lag nicht im Code, sondern in der tatsächlichen Conversation bei ElevenLabs. Dort sah ich, welche Variablen wirklich ankamen: die kleinen — alle da. Die große mit dem ganzen Firmen- und Dokument-Kontext — verschwunden. Lautlos.

04Die Wurzel

Root Cause

Ich habe eine Dynamic Variable als Daten-Pipeline für 20.000 Zeichen missbraucht. ElevenLabs verwirft überlange Variablen still — kein Fehler, kein Log. Die 2.379-Zeichen-Variable kam durch, die 20.000er nicht. Also rannte der Platzhalter {{briefing_context}} im Agent-Prompt ins Leere.

Falsches Werkzeug für den Job. Dynamic Variables sind für Kurzwerte gedacht — einen Namen, eine Firma. Nicht für ein ganzes Dossier.

05Der Fix

ElevenLabs kennt den richtigen Weg für große Inhalte: den Prompt-Override. Man überschreibt den kompletten System-Prompt pro Gespräch — großes Limit, genau dafür gebaut. In den Security-Settings des Agenten war das sogar schon freigeschaltet. Es wurde nur nicht genutzt.

// web/app/voice/page.tsx — das ElevenLabs-Widget
<elevenlabs-convai
  agent-id={AGENT_ID}
-  dynamic-variables={JSON.stringify({ briefing_context: prompt })}  // 20k → still verworfen
+  override-prompt={preBrief.system_prompt}          // voller Prompt, großes Limit
+  override-first-message={preBrief.first_message}
></elevenlabs-convai>

Eine Zeile raus, zwei rein. Der gesamte Briefing — Persona, Firmen-Kontext, Hypothesen, Dokument-Recap — landet jetzt direkt im Prompt. Ada sieht alles.

06Die Lektion

  • Der Bug saß in keiner Komponente — er saß zwischen zweien. Jeder einzelne Baustein funktionierte. Der Fehler lebte in der Übergabe.
  • „✓ verarbeitet“ hat gelogen. Die UI bestätigte den Upload und nährte das falsche Vertrauen. Erfolgsmeldungen ersetzen keinen Beweis.
  • Daten an jeder Grenze prüfen schlägt Raten. Fünf Checks, vier grün — der eine rote zeigte exakt, wo es brach. Ohne diese Methode hätte ich Stunden im Backend gesucht, das nie das Problem war.
  • Stille Fehler sind die teuersten. Kein Crash, kein Log — nur ein Agent, der sich dumm stellt. Da hilft nur: an der Systemgrenze nachsehen, was wirklich ankam.
